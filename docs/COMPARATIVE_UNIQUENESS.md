# PubliPulse comparative uniqueness review

This document records a bounded desk comparison. It is not a claim that PubliPulse is globally unique.

## What existing systems already do well

- **Africa CDC EMS:** continental event-based surveillance, signal/event management, risk assessment, notifications, response coordination and interoperability are established capabilities.
- **DHIS2 Tracker/Event programs:** event and tracked-entity workflows, follow-up, notes, analytics and case monitoring are established capabilities.
- **WHO EWARS:** rapid early warning and response, including offline/low-connectivity deployment patterns, is established capability.
- **Kenya m-Dharura:** community, facility and other event-based surveillance, real-time reporting, feedback/escalation and offline/SMS operation are established capabilities.
- **Nigeria SITAware:** low-bandwidth event management, notifications, event-level accountability and post-event learning/7-1-7 review are documented capabilities.
- **Commercial critical-event tools such as Everbridge:** detection, communication, response workflows, audit/reporting and after-action analytics are established capabilities.

## Where PubliPulse should differentiate

PubliPulse should not claim ownership of detection, EBS, dashboards, messaging, case management, or generic interoperability. The defensible product boundary is narrower:

> **Outcome and accountability overlay:** make unresolved outcomes, stalled ownership, recurrence after action, response decay, resource blockers and bounded operational learning persistently visible after an event is administratively closed.

The differentiator must therefore be demonstrated by workflow evidence, not marketing language.

## Nine-point validation status

1. Response effectiveness decay — implemented in the product model.
2. Reporter feedback — implemented as an append-only feedback/evidence path; delivery-provider integration remains deployment-specific.
3. Intervention-resistant learning queue — implemented as a prioritization and review model.
4. 7-1-7 alignment — implemented as explicit notification/response clocks plus an outcome-completeness clock.
5. Resource intelligence — implemented through normalized blocker taxonomy and aggregate views.
6. DHIS2/outcome overlay — provider-neutral contracts and controlled adapter exist; no live external integration is claimed.
7. Uncertainty/non-resolution — implemented as explicit states and non-causal interpretations.
8. Offline action/outcome workflow — implemented as conflict-aware local mutation queuing in the web field workspace; production use requires device-level secure storage and deployment controls.
9. Uniqueness validation — this desk review is complete as a baseline; field validation remains necessary before making uniqueness claims.

## Validation protocol for a real pilot

Before public claims, compare the same closed-event cohort across the incumbent workflow and PubliPulse for 4–6 weekly review cycles. Measure:

- proportion reaching verified, owned, acted and measured states;
- proportion closed without resolution evidence;
- recurrence after action;
- time to notification and response start where explicitly recorded;
- outcome evidence completeness;
- blocker distribution;
- expert-review decisions and subsequent outcome evidence;
- whether the PubliPulse queue changes a documented management decision.

A successful result should be framed as an observed operational improvement in the pilot context, not proof of causal effectiveness or global uniqueness.
